# RAG Pipeline Refinements (RAG Fine-Tuning v3)

This document outlines the refinements made to the Study Material RAG pipeline to resolve the issue where small high-density files (e.g., VLM descriptions of diagrams like `Zachman framework - sweta dargad.jpg`) were being sidelined by large files (like `netflix_data.csv` containing 390 chunks) in the merged vectorstore.

---

## 1. Identified Issues & Diagnostic Summary

1. **Missing Merged BM25 Index (`bm25_index.pkl`)**: 
   * While the pipeline generated individual BM25 indexes for each file during Phase 2, the **Phase 3 merge** step only merged the FAISS indexes. The final combined complete vectorstore had no unified BM25 index.
   * This forced the query pipeline to print `"dense-only"` warnings and fall back to purely dense vector retrieval.
2. **Dense Domination by Large Files**:
   * Out of 767 total chunks in Study Material 10, `netflix_data.csv` contributed 390 chunks (over 50%).
   * Dense-only cosine distance search is statistically prone to flooding the top-k results with chunks from large files, especially when search queries match general vocabulary.
   * This caused the single-chunk diagram `Zachman framework - sweta dargad.jpg` to be squeezed out of the top-k dense results, even though it was highly keyword-relevant.
3. **Noisy Context Ordering**:
   * Even when keyword-relevant files managed to tie or place in RRF (Reciprocal Rank Fusion), the LLM context was populated strictly in retrieval score order. Noisy, irrelevant spreadsheet chunks populated the beginning of the context, causing the LLM to reply with: `"The provided context does not contain information about this topic."`

---

## 2. Refinement Implementation Plan

To solve this, three architectural modifications were implemented:

### A. Rebuilding a Unified BM25 Index on Merge
* **Change**: Added a step in `StudyMaterialProcessor._phase3_merge()` to build a fresh `BM25Okapi` sparse index from the combined FAISS docstore.
* **Result**: The complete vectorstore now always saves `bm25_index.pkl` containing the full vocabulary across all files, enabling robust hybrid search.

### B. BM25-First Context Reordering
* **Change**: Modified `VectorStoreManager.query()` to segment retrieved documents into BM25-boosted results (exact keyword hits) and dense-only results.
* **Result**: Chunks containing exact keyword matches are automatically bubble-sorted to the very top of the prompt context contextually. Dense-only vector neighbors follow. This ensures the LLM's attention is focused directly on target keywords first, preserving RRF ranking for API outputs.

### C. Granular Per-File Chunk Metadata Logging
* **Change**: Added `_save_chunks_metadata()` to the processor. 
* **Result**: Saves a `{stem}_chunks.json` file inside the `text/` directory for every processed file. This provides instant visibility into the exact text and metadata segments generated by the chunking router (e.g., AST parses, spreadsheet row mappings, VLM descriptions) for diagnostic inspection.

## 3. Detailed Code Modifications

### `apps/core/services/study_material_processor.py`
1. **Unified BM25 Rebuild**:
   ```python
   # Rebuild BM25 from the merged docstore so hybrid search works on the

   # FAISS.merge_from — they must be rebuilt from the merged corpus).
   self._rebuild_bm25(merged_vs, tmp_path)

   @staticmethod

       # Writes a formatted JSON log containing all enriched chunks, page numbers, row-ranges, and token mappings.
   ```

### `apps/core/services/vectorstore.py`
1. **Context Ordering Optimization**:
   ```python
   # --- Reorder context: BM25-boosted chunks lead, dense-only follow ---
   bm25_doc_ids = {id(doc) for doc, _ in bm25_results} if bm25_results else set()
   bm25_led = [(doc, s) for doc, s in final_docs if id(doc) in bm25_doc_ids]
   dense_only_docs = [(doc, s) for doc, s in final_docs if id(doc) not in bm25_doc_ids]
   context_ordered = bm25_led + dense_only_docs
   ```
2. **Prompt Population**:
   * Uses `context_ordered` to build the annotated context string (`[Source: ...]`) sent to the LLM.
